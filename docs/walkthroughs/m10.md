## 1. How it works

* **The twin picks the database.** After `config/application.rb` loads, the worker reads
  the app's test database configuration (or the `DATABASE_URL` Doubletrack was started
  with). For PostgreSQL it points its own `DATABASE_URL` at a private database on that
  server, `dt_<hash of the run's work dir>_<role>`. The coordinator didn't change.
* **Snapshots are template databases.** Control A builds the template from `db/schema.rb`,
  seeds and fixtures. Before every session each twin runs
  `DROP DATABASE own WITH (FORCE)` and then `CREATE DATABASE own TEMPLATE template`, over a
  separate `PG::Connection` to the `postgres` database. The `FORCE` also ends connections
  held by the app's own threads (R18). Servers older than 13 are refused at boot.
* **Reproductions** ship `snapshots/<hash>.pg.json`, a recipe with the seed and whether
  seeds and fixtures were loaded. The repro's twin rebuilds the template from it.
* **Cleanup:** each twin drops its database at shutdown, and control A also drops its
  templates.
* **Found along the way:** `Bundler.with_unbundled_env` drops every `BUNDLE_*` variable,
  so `BUNDLE_WITH=postgresql` never reached the twins and they couldn't load `pg`. Twins
  now get the user's own Bundler settings from an allowlist (`BUNDLE_WITH`, `BUNDLE_PATH`,
  `BUNDLE_DEPLOYMENT`, …), but never Bundler's bookkeeping variables (R1). A spec covers it.
* **shop** has an optional PostgreSQL variant: `pg` sits in an optional bundler group, and
  `SHOP_DATABASE_URL` switches the test database.

## 2. Results

Locally (PostgreSQL 17 in Docker under WSL2) and in CI, `spec/integration/postgresql_spec.rb`
checks the following:

| Check | Result |
|---|---|
| each twin on its own database (`run.json` `twins.*.database`) | `postgresql`, `dt_…_control_a` etc. |
| determinism: control A vs control A′ differences | 0, as on SQLite |
| findings | `f-bb3068808cf1`: **the same finding id as on SQLite**, reproduction verified |
| the generated Minitest file, run for real on each Gemfile | passes on 8.0, fails on 8.1 with "unexpected end of input" |
| databases named `dt_%` afterwards | none |

**Cost.** On shop (5 sessions, 14 requests), replay took 15.2 s on PostgreSQL against 3.96 s
on SQLite. Measured with psql's timing on the same server, one `DROP … WITH (FORCE)` plus
`CREATE … TEMPLATE` takes 300–700 ms per twin. The three twins restore at the same time,
which adds about 2 s per session here. `STRATEGY FILE_COPY` was no faster than the default
`WAL_LOG`. The design note had guessed 50–300 ms; these measurements replace that guess.

## 3. Limitations

* About 2 s per session for restores on this machine. Preparing the next copy ahead of time
  and renaming it into place would hide most of that; it's planned with the scale work
  (M12).
* PostgreSQL 13+ only. MySQL isn't supported.
* A twin that crashes leaves `dt_…` databases behind. The coordinator has no PostgreSQL
  client to sweep them.
* Once, during development, a template database was left behind after a run. It didn't
  happen again in three local runs or in CI, and the cause wasn't found.
* A PostgreSQL repro rebuilds its template from the current schema, seeds and fixtures,
  so it can drift if those change after the run.
* Database-side time (`now()`) isn't frozen.
