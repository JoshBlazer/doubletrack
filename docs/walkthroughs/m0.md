# M0 walkthrough: twins talk

**Exit check:** `bin/doubletrack-spike fixtures/apps/shop` shows a response from each
version, with versions reported in `hello`.

**Result: passes locally (2026-11-03). Not yet run in CI** because the repository has no
GitHub remote yet. M0 is not "done" until the `integration` job is green.

Machine: WSL2 (Linux 6.6.114.1-microsoft-standard-WSL2, x86_64), Intel Core i7-7600U
@ 2.80 GHz, 4 logical CPUs, 8 GB RAM. Ruby 3.4.12 (rbenv). Timings below are single runs
on this laptop, not benchmarks.

## 1. The fixture app dual-boots

`fixtures/apps/shop` was generated with `rails _8.0.5_ new` (SQLite, minimal) and given
users, orders, a mailer (`OrderMailer#confirmation`), a job (`OrderConfirmationJob`,
enqueued `after_create_commit`), a cache read/write (`orders/summary`), and one outbound
HTTP call (`ExchangeRates.rate` via `Net::HTTP`). The Gemfile branches on `next?`, and
`Gemfile.next` is a symlink to `Gemfile` (ADR 0001).

```console
$ grep -E "^    rails \(" fixtures/apps/shop/Gemfile.lock fixtures/apps/shop/Gemfile.next.lock
Gemfile.lock:    rails (8.0.5.1)
Gemfile.next.lock:    rails (8.1.4)

$ cd fixtures/apps/shop && bin/rails test
5 runs, 16 assertions, 0 failures, 0 errors, 0 skips

$ BUNDLE_GEMFILE=Gemfile.next bin/rails test
5 runs, 16 assertions, 0 failures, 0 errors, 0 skips
```

What this shows:
* `hello` reports two **different** Rails versions from the same app checkout. The spike
  exits 2 if they're equal, which is the guard against Bundler leaking between
  coordinator and twins (RISKS R1). *That negative path hasn't been exercised against a
  real app yet.*
* Both twins run in the `doubletrack` environment overlaid from the gem (ADR 0009);
  `rails_env` in `hello` is `doubletrack` and the app has no such file.
* The app's request logging went to the twin log in the run's temp directory, not to
  the protocol stream and not into the app's `log/` (checked with `--keep`).

## Surprises and notes

* **First CI run caught a real Bundler leak (RISKS R1).** Run 41552751273: the spike
  step passed, but `rake spec:integration` failed with `Bundler::GemNotFound` in both
  twins. Cause: under `bundle exec` with a configured bundle path (setup-ruby's cache),
  Bundler exports `GEM_HOME`/`GEM_PATH`. The integration spec launched the spike with
  Bundler's auto-load variables cleared, so the coordinator ran *without* Bundler,
  skipped `with_unbundled_env`, and handed the gem's `GEM_HOME` to the twins. It didn't
  reproduce locally because no bundle path was configured. Fix: the coordinator always
  `require "bundler"` (API only, no `bundler/setup`) and spawns inside
  `Bundler.with_unbundled_env`. A regression spec reproduces the leak in a Bundler-free
  subprocess; it failed before the fix and passes after it.
* The same run failed on Ruby 3.2 at `bundle install`: `parallel` 2.x (a rubocop
  dependency) requires Ruby ≥ 3.3. The dev Gemfile now pins `parallel < 2`.

* `wsl.exe -- cmd` runs the command through a login shell, which expanded `$?` early.
  Exit codes in this walkthrough were all captured with `wsl.exe --exec`.
* Rails 8.0's generated `test.rb` sets `eager_load = ENV["CI"].present?`. The
  `doubletrack` overlay forces `eager_load = false`, so CI and local twins behave the same.
* Rails 8.0's `test.rb` uses `:null_store` for the cache, so the shop's `orders/summary`
  cache write is invisible today. M1 needs the overlay to use a memory store so cache
  writes can be recorded.
