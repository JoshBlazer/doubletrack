# M8 walkthrough: `init`, `doctor` and a releasable 0.1.0

**Exit check (ROADMAP):** `init` dual-boots a fresh Rails app for the next version;
`doctor` explains a broken setup; `gem build` + install + `doubletrack run` from the
installed gem.

**Status: done.** CI [run 42114755002](https://github.com/JoshBlazer/doubletrack/actions/runs/42114755002),
all 10 jobs ✓ (the new one: `installed gem runs shop`). Design:
[`docs/design/setup.md`](../design/setup.md); ADRs 0033 (`init`), 0034 (`doctor`), 0035
(releases). Publishing 0.1.0 to rubygems.org is the maintainer's step
([`docs/RELEASING.md`](../RELEASING.md)).

## 1. `doubletrack init`

On a copy of shop with a plain Rails 8.0 Gemfile and no `Gemfile.next`
(`spec/integration/setup_spec.rb`):

```console
$ doubletrack init path/to/shop --to 8.1 --install
Current Rails: 8.0.5.1 (Gemfile.lock)
Wrote Gemfile.next with gem "rails", "~> 8.1.0", and Gemfile.next.lock (a copy, so Bundler moves only Rails and what it needs).
Gemfile, Gemfile.lock and your code are unchanged.
Running BUNDLE_GEMFILE=Gemfile.next bundle install...
...
Next:
  doubletrack doctor                           # check the setup; boots both versions
  doubletrack capture                          # sessions from your integration tests
  doubletrack run                              # replay, compare, report
```

Bundler resolved Rails 8.1.4.1, the newest 8.1 patch, from the copied lockfile. The spec
checks that `Gemfile` is byte-for-byte unchanged.

* Without `--to`, the target is the next minor version (7.2 → 8.0 across the major).
* `--to main` points at `github: "rails/rails", branch: "main"`.
* A Gemfile that already defines `next?` (the next_rails convention) gets a symlink and a
  note to edit its `if next?` branch.
* An existing `Gemfile.next` is never overwritten without `--force`.

## 2. `doubletrack doctor`

On Campfire under the wrong Ruby it warns, and under the right one everything passes,
including booting both Rails revisions:

```console
$ doubletrack doctor ~/m6/pr423 --no-boot          # under Ruby 3.4.12
  warn  ruby: the app's .ruby-version says 4.0.9, Doubletrack runs both twins on 3.4.12
        fix: run Doubletrack under Ruby 4.0.9 (for example RBENV_VERSION=4.0.9)
  ...
Ready (1 warning): run `doubletrack capture`, then `doubletrack run`.

$ RBENV_VERSION=4.0.9 doubletrack doctor ~/m6/pr423
  ...
  ok    boot: control A booted Rails 8.2.0.alpha (e3d5c569d2) in 9.1 s, candidate B Rails 8.2.0.alpha (8b06b0eb98) in 10.4 s
Ready: run `doubletrack capture`, then `doubletrack run`.
```

The checks are: platform, Ruby, dual-boot files, Rails versions, both bundles installed
(`bundle check`), database (SQLite and `db/schema.rb`), HTTP clients that bypass
`Net::HTTP`, sessions, git and boot. Each failure carries a fix. Unit specs build broken
apps for each failure. The integration spec moves `Gemfile.next.lock` aside and gets
`FAIL  dual boot: missing Gemfile.next.lock` with `fix: BUNDLE_GEMFILE=Gemfile.next bundle install`,
exit 1.

## 3. 0.1.0, packaged

* `Doubletrack::VERSION` is `0.1.0`, and `CHANGELOG.md` has a `[0.1.0]` section marked
  "not yet published".
* `script/installed_gem_check` builds the gem, installs it into an empty directory, and
  runs that copy from outside the repository. It replays shop (exit 1, one verified
  finding, report written) and captures shop's tests. CI runs it on every push.
* `release.yml`, on a `v*` tag:
  1. checks that the tag matches the version;
  2. runs lint, the unit specs and the packaging check;
  3. publishes with RubyGems trusted publishing (OIDC, no stored key);
  4. attaches the `.gem` to a GitHub release.
* The name `doubletrack` was free on rubygems.org when checked (2026-11-05).

## 4. Limitations

* `init` replaces only a `gem "rails"` statement. Apps that list `railties` and the
  frameworks separately need `Gemfile.next` edited by hand.
* `--install` uses the network through the user's own Bundler, as `bundle install` would.
  Doubletrack itself makes no network calls.
* `doctor` reads the test database adapter from `config/database.yml` with ERB stripped,
  so an adapter chosen in ERB isn't detected.
* The release workflow hasn't run yet: it needs the rubygems.org trusted publisher set up
  and a tag pushed, both the maintainer's steps.
