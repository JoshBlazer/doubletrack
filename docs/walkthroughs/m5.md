## 1. Order of work

1. Design note and ADRs, then specs committed **red** (`dcdc24d`):
   * record builder, assembler, session snapshot kinds, CLI `capture`;
   * the integration exit check.

   In the same commit, shop gained:
   * test fixtures (`users.yml`, `orders.yml`);
   * one test that reads a fixture record by id (`orders(:paid)`);
   * `doubletrack/http_stubs.json`.

   Shop's own tests pass on both Rails versions (8 runs, 24 assertions each).
2. Implementation:
   * `Capture::Record` and `Capture::Probe` (in the test process);
   * `Capture::Assembler` and `Capture::Runner`;
   * `Session` snapshot kinds and `test_status`;
   * a `fixtures` option in `Snapshot#build`;
   * one template per snapshot kind in `Run`, plus fidelity;
   * per-repro snapshots;
   * CLI `capture`;
   * the fidelity section on the coverage page.
3. Design correction made before the first run. The plan was to load the probe through
   `RUBYOPT`. That would also load it into the `bundle` CLI process, and possibly
   activate a global `activesupport` before the app's bundle was set up (a version
   conflict). Instead, capture runs `ruby -r<probe> SCRIPT ARGS` itself. The probe sets
   up the app's bundle first and then registers lazy load hooks.
4. Two gaps I found by re-reading what the specs claimed:
   * The fixture-id example checked only control A while saying "on every twin". It
     now checks all three.
   * ADR 0025 claimed capture was checked on both Rails versions, but nothing ran it on
     8.1. I added `--gemfile`, plus an example that captures on `Gemfile.next` and
     requires byte-identical sessions. It passes.

### Is fidelity a real measurement? (negative control)

I removed the HTTP stubs from the captured sessions and replayed again:

```console
  Findings: 1 new  (data-changing 0, user-visible 1, cosmetic 0)
    [user-visible] GET /orders/:id(.:format): exception.message changed  (1 session, f-bb3068808cf1)
  Capture fidelity: 12/13 requests replayed with the status their test saw (mismatches listed on the coverage page)
```

The one mismatch is `GET /orders/1032760124.json?currency=EUR`: 200 in the test,
`raised` on replay. The test swaps the rates client at the app level. The replay has
no stub, so the request is blocked and its empty body fails to parse. That also
re-surfaces M3's real 8.0 → 8.1 finding, **with the same id** `f-bb3068808cf1` as when
it came from the hand-written sessions. Its reproduction was built on the fixtures
snapshot, and it passes on 8.0 and fails on 8.1 when run under Minitest.

## 3. What this shows, and what it doesn't

* **Shown on shop:**
  * every request-making integration test becomes a session, with its requests in
    order and unencoded (params and `as: :json`);
  * the sessions replay with the status the tests saw (13/13), including a fixture
    id;
  * the probe works on 8.0 and 8.1;
  * the app's tracked files are untouched.
* **Shown by unit specs only:**
  * the RSpec request-spec path (test naming via `RSpec.current_example`);
  * skip reasons (uploads, raw bodies, non-header env, OPTIONS);
  * redaction;
  * deduplication.

  Shop has no RSpec request specs and no secrets in its tests.
* **The honest headline is 0 findings.** shop's captured traffic doesn't hit the one
  known 8.0 → 8.1 difference unless the stubs are removed. Capture adds coverage; it
  doesn't add findings by itself. Route coverage from tests alone is 5 of 7 (no `/up`,
  no root): fewer routes than the hand-written sessions, which reach 7 of 7.
* **Limits:**
  * system tests, model tests and anything outside the integration session aren't
    captured;
  * app-level stubs and `sign_in` helpers don't carry over (fidelity flags them);
  * redaction is value-based;
  * outbound HTTP needs `doubletrack/http_stubs.json`.
