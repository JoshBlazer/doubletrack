# M6 walkthrough: a real open-source app (once-campfire)

**Exit check (ROADMAP):** published report URL + walkthrough + any upstream issues filed.

**Status: in progress.** The run and this walkthrough are done locally. Publishing the
report and contacting the maintainers (RISKS R9) wait for the maintainer's go-ahead,
one step at a time.

## 1. The app and the upgrade

* **App:** [basecamp/once-campfire](https://github.com/basecamp/once-campfire), MIT
  licence, SQLite, Minitest with about 650 tests, 154 routes.
* **Upgrade:** [PR #423](https://github.com/basecamp/once-campfire/pull/423), "Update
  Rails to main at 8b06b0eb", merged 2026-11-04. It changes only `Gemfile.lock`:
  * Rails main `e3d5c569` → `8b06b0eb` (1,049 commits, including the 2026-11-04 security
    release, merged into main by `6782df4a`);
  * rack 3.2.7 → 3.2.8, addressable 2.9.0 → 2.9.2, actionview's new
    `rails-html-sanitizer >= 1.7.2` floor.

  The application code is identical on both sides, which is the situation Doubletrack
  is built for. The PR also makes testable claims: the bump "breaks nothing", the new
  `message_serializer = :json` default is harmless, and the `Forwarded` /
  `X-Forwarded-For` spoofing check doesn't reach Campfire.
* **Why not the earlier upgrade** (`9d75c8b7e`, Rails main `1a02651` → `e3d5c569`, with
  app changes): at `1a02651`, with Minitest 6.0.6, `bin/rails test` loads no test files.
  Minitest 6 made plugin loading opt-in and that Rails revision doesn't load its own
  plugin (later Rails main calls `Minitest.load :rails`). There was nothing to capture.

## 2. Setup (no change to Campfire's code)

```sh
git clone https://github.com/basecamp/once-campfire.git
git -C once-campfire worktree add ../pr423 86dd525e1~1     # main just before the PR
cd pr423
cp Gemfile Gemfile.next                                     # same Gemfile...
git -C ../once-campfire show 86dd525e1:Gemfile.lock > Gemfile.next.lock   # ...the PR's lockfile
bundle install && BUNDLE_GEMFILE=Gemfile.next bundle install
# system packages Campfire's CI installs: libvips (loaded at boot), ffmpeg
```

Then, from the Doubletrack repository:

```sh
bundle exec exe/doubletrack capture ~/m6/pr423
bundle exec exe/doubletrack run ~/m6/pr423
```

## 3. What Doubletrack got wrong first, and the fixes

Campfire was the first app Doubletrack hadn't been written against. Each problem was
fixed in Doubletrack with a failing spec first:

| Symptom on Campfire | Cause | Fix |
|---|---|---|
| `run` would stop with "dual boot not effective" | both sides report `Rails.version` `8.2.0.alpha` | twins report the git revision; labels read `8.2.0.alpha (e3d5c569d2)` (`d9de98c`) |
| `capture`: boot error shown without its message | only the last 30 lines of output were shown | keep the exception line above a backtrace (`f4a7fcd`) |
| `capture`: 649 tests ran, 0 requests captured | the lockfile says `BUNDLED WITH 4.0.13`; Bundler re-executes the test process and drops `-r<probe>` | probe in `RUBYOPT`; twin pipes stay inheritable until the bundle loads (ADR 0028, `166fca5`) |
| 25 of 48 findings were `no such table: bans` on a random twin | Campfire's WAL-checkpoint thread holds its own connection; restore deleted and copied the file under it | restore through SQLite's backup API (ADR 0029, `166fca5`) |
| generated Minitest names like `…_alpha__e3d5c569d2__behavior` | parentheses in the new label | collapse runs (`8c76d8f`) |

CI for these fixes: [run 42046719066](https://github.com/JoshBlazer/doubletrack/actions/runs/42046719066), all 9 jobs ✓.

## 5. Limitations seen on this app

* **Not replayable, skipped and reported by capture:** 23 bot-API tests that send a raw
  string body, and 3 file uploads (`Rack::Test::UploadedFile`).
* **Capture fidelity 91%:** the mismatches are requests whose outcome depended on state
  built inside the test (records created in `setup`, signed Active Storage URLs that
  have expired by replay time, mocha stubs). The coverage page lists each one.
* **Background threads:** Campfire's web-push pool runs during replay. One push
  subscription delete appeared on candidate B only and didn't reproduce: a finding
  that verification correctly labels "not verified" (R18).
* **Five sessions named `integration-session-NNN`:** one test signs up five users at
  once, each through its own integration session in a thread; the probe's test name is
  per thread. Each stays its own session (separate cookies), but unnamed.
* **Route coverage 44%:** Action Cable, system tests and the bot API aren't replayed.
