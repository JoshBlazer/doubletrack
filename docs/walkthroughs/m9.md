## 1. `summary.md`

Every `run` and `report` now writes a GitHub-flavored summary next to `run.json`. On shop:

```markdown
<!-- doubletrack-summary -->
### Doubletrack: Rails 8.0.5.1 → 8.1.4: ❌ Not ready to ship

**1 new finding in 1 change** (data-changing 0, user-visible 1, cosmetic 0) · 14 requests in 5 sessions · route coverage 7 of 8 (88%) · 0 noisy differences filtered

| Severity | Change | Where | Reproduced | Likely cause |
|---|---|---|---|---|
| user-visible | `exception.message`: "unexpected token at ''" → "unexpected end of input at line… | `GET /orders/:id(.:format)` | 1/1 | json `ext/json/ext/parser/parser.c` (source file) |

If a change is expected: `doubletrack accept c-8a5d176afec2 --reason "..."` (records it in `doubletrack.baseline.yml`; commit that file).

<details><summary>16 bundle changes</summary> … </details>
```

The summary stays under 60,000 characters (GitHub's comment limit is 65,536). The table
lists at most 25 changes, and its cells are escaped and shortened.

## 2. The action

`action.yml` at the repository root is a composite action:
1. it installs the gem from its own checkout;
2. it installs both bundles, optionally captures, and runs;
3. it appends the summary to the job summary and uploads the results (without raw traces)
   as `doubletrack-report`;
4. with `comment: "true"` on a pull request, it updates the one comment that starts with
   the marker, or creates it;
5. it applies `fail-on`.

## 3. The proof in CI

The `action on shop` job runs the action twice with `uses: ./`, the same way a user would
run it (step outcomes from run 42116504407):

| Step | Result |
|---|---|
| Doubletrack (fail-on never) | success: verdict `not_ready`, 1 change, 1 finding, exit code 1 |
| Outputs and summary match the results (`script/check_action_outputs`) | success |
| shop is not ready, with one change | success |
| Doubletrack (fail-on user-visible), this time capturing first | the step failed, as it should |
| fail-on user-visible failed the step | success |

`script/check_action_outputs` compares the outputs with `run.json`, and checks that the
summary has the marker and the verdict. It also checks that every change has a row with
its likely cause, and that the `accept` hint names the first change. Run locally against
the wrong verdict, it reports `verdict output ready != run.json not_ready` and exits 1.

## 4. Limitations

* The PR comment path ran only in its error-tolerant form here: CI runs on pushes, not pull
  requests, so the comment step was skipped. It uses `gh api` on the issue comments of the
  PR. Tokens from fork PRs are read-only, so it warns instead of failing.
* The action needs the app's Ruby and system libraries from earlier steps.
* No SARIF output yet (layer L4).
