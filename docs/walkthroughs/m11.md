# M11 walkthrough: a Ruby per side

**Exit check (ROADMAP):** candidate B runs on a different Ruby than control A, in CI.

**Status: done.** CI [run 42243141650](https://github.com/JoshBlazer/doubletrack/actions/runs/42243141650),
all 13 jobs ✓. The new job is `integration two Rubies`: control A on Ruby 3.4 and candidate
B on Ruby 3.3, both installed by `ruby/setup-ruby` in the tool cache. Design:
[`docs/design/rubies.md`](../design/rubies.md); ADR 0038.

## 1. What changed

* `ruby` and `next_ruby` in `doubletrack.yml`, and `--ruby` / `--next-ruby` on `run`
  (`--ruby` on `capture`). Each takes `auto`, `current`, a version or a path. `auto`, the
  default, uses the app's `.ruby-version` when that Ruby is installed.
* `RubyLocator` finds installed Rubies:
  * the rbenv, asdf, mise, chruby and rvm directories, and the GitHub Actions tool cache;
  * each candidate is run once to confirm its version.
  * It never installs anything.
* A twin on another Ruby gets no `GEM_HOME`/`GEM_PATH`, that Ruby's `bin` first on `PATH`,
  and no `RBENV_VERSION` (or asdf or mise equivalent).
* `doctor` names each side's Ruby, and fails when a configured Ruby isn't installed.
* **Bug found while building it:** the version probe inherited `bundle exec`'s `RUBYLIB`,
  which loaded Ruby 3.4's Bundler into Ruby 4.0. The probe now clears Bundler's variables
  and reads only stdout.

## 3. Limitations

* Rubies are found, never installed.
* Each bundle must be installed for its own Ruby.
* Changes caused by the Ruby upgrade and by the Rails upgrade share one report.
* Reproduction specs run in the user's test process, so each side's spec must be run with
  that side's Ruby.
