# M2 walkthrough: session replay

> A record of the project at the end of this milestone. Later milestones changed some
> details; the README, `docs/ARCHITECTURE.md` and `docs/formats/` describe the current code.

**Exit check:** the same session replayed twice on the same version produces identical
normalized traces.

**Result: done (2026-11-03).** `spec/integration/replay_spec.rb` passes on both twins
(Rails 8.0.5.1 and 8.1.4), locally and in CI [run 41592499206](https://github.com/JoshBlazer/doubletrack/actions/runs/41592499206): all jobs green, and the
integration job reports `32 examples, 0 failures` (M0 + M1 + M2).

Design: [`docs/design/replay.md`](../design/replay.md). Formats:
[`docs/formats/session.md`](../formats/session.md),
[`docs/formats/trace.md`](../formats/trace.md) (trace_version 2). Decisions:
* ADR 0014: jobs are performed inline.
* ADR 0015: Doubletrack's own clock, with `SecureRandom` left alone.
* ADR 0016: protocol schema_version 3.

Machine: same as M0 (WSL2, i7-7600U, Ruby 3.4.12).

## 1. Order of work

1. The design note, session format and ADRs came first (commit `5e1fb5b`).
2. Next came the exit-check spec `spec/integration/replay_spec.rb` and unit specs for the
   clock, the session loader and the normalizer. These were committed and **run red**
   before any implementation (`4929363`): they failed to load because nothing existed yet.
3. Implementation (`ecdcc42`):
   * `Twin::Clock` and `Twin::Snapshot`;
   * the recorder at trace v2, with jobs performed inline;
   * `Session` and `Normalize::Trace`;
   * `prepare_snapshot` and the new `run_session` inputs in the twin;
   * removal of the boot-time schema stopgap.
4. **First integration run: 17/17 failing**, and the cause was a design mistake. The
   design froze the clock at the session's `started_at` while building the template.
   Rails 8.1 then refused to load `db/schema.rb`, because it checks migration timestamps
   against "now":

   ```
   Invalid timestamp 20261102235353 for migration file: create_users.
   Timestamp must be in form YYYYMMDDHHMMSS, and less than 20260116093000.
   ```

   The session's time (2026-01-15) predates the app's migrations (2026-11-02). The fix is
   to build the template on the real clock, which is safe because one template is shared by
   every twin. The design note now records this.
5. Second run: 17/17 green. The M1 spec and the spike were moved onto snapshots, and the
   full integration suite is 32/32.

## 3. Is the normalizer hiding anything?

An identical-after-normalization check proves little if the normalizer throws too much
away. `tmp/m2_evidence.rb` (an ad-hoc script, not committed) replays the session on A
and A′ and lists every **raw** leaf that differs:

```
raw differing leaves between A and A': 27
      6  .duration_ms
      3  .response.headers.set-cookie
      6  .response.headers.x-request-id
      6  .response.headers.x-runtime
      6  .session.session_id
normalized traces equal: true
```

Only the five fields the design names as volatile differ. Everything else is identical
byte for byte *before* normalization: SQL binds (including `created_at`), row ids, response
bodies, `etag`s, mail bodies, cache values, and the jobs performed inline.

## 4. What this shows, and what it doesn't

* **Isolation works.** Ids restart at 1 on every replay, and the cache and mail are empty
  at session start. The same twin can replay a session again and get the same result.
* **Cookies carry across requests.** Request 3 sees both orders that requests 1 and 2
  stored in the session.
* **Jobs performed inline show what a job does (ADR 0014).** The order confirmation mail,
  which M1 couldn't see, is now recorded under `performed_jobs[0].mail`.
* **Not covered:**
  * `SecureRandom` values the normalizer doesn't know about. M3's A/A′ noise mask has to
    absorb them.
  * Time read by SQLite itself (`CURRENT_TIMESTAMP`).
  * Class-level state an app keeps in memory across sessions (memoized constants, class
    variables). Snapshots reset the database, not Ruby objects.
  * Multiple databases.
